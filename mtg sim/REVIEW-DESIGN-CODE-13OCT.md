# Sim Design and Code Review

Review doc, 13 Oct 2026 · live copy: https://claude.ai/code/artifact/00f7b93a-8777-424a-b0c4-c7d97f0a80d4

## The verdict

The sim's design is better than its own brief asked for and the code is further along than its page admits; the gap is between them. Star Shard's principles (one region is one thing; the answer first; rows not cards; ceremony scales inversely with frequency; say the real word; never narrate the method) are mostly honoured on the Brewer v3 screens, and the engine work of the last week (pilot, calibration, functional check, dead cards) is real. What is not elegant yet is the seam: a 145 KB single-file UI carrying 125 literal strings and 618 inline styles, an 80 KB `server.js` that owns every route, and a Results tab that now shows five kinds of number (game 1, boarded, match, calibrated, benchmark) where the brief asked for one answer and a range.

Five changes matter most, in order:

1. **Make Results answer one question.** "How does this list do in this week's field" is one number with a range, then the opponent rows. Game 1 / boarded / benchmark / calibration move to a level-two disclosure on each row, which is the two-level rule from UI-PRINCIPLES §1.4. Today they share the headline's weight.
2. **Decide the brand question once.** The sim ships Manrope, JetBrains Mono and lime #C5EC7A on near-black; Star Shard v2 is Cormorant Garamond, Varela Round, amber and parchment, and its skill says "no third font, ever." The README calls the sim "separate from Star Shard; it only shares the domain." Either it is its own product with its own two-page system, written down, or it adopts the Star Shard one. Both are fine; the undocumented middle is where drift starts (DESIGN-SYSTEM.md opens with the 118-colour audit that drift produced last time).
3. **Split the page and the server along the seams that already exist.** The Component class is 580 lines inside the HTML; `server.js` holds auth, queue, brews, codex, worker, usage and meta routes in one file. Neither needs a framework; each needs its files to match the module map the README already draws.
4. **Delete the honest-but-noisy states.** "Not played, counted as even", "Not counted · …", "—" cells for pod stats, "Sources · blended by default" with a snapshot picker that has one source: each is the engine's uncertainty printed as UI. Show the state in one place (the run header) and remove the rest until the feature behind it exists.
5. **Finish the three screen archetypes.** Coach is a Reading screen and reads like one (eyebrow, answer, prose, one link down). Results should be a Reference screen (sections of rows), Deck a Collection screen (the list as the hero). Today Results mixes a hero number, a share-of-field bar chart, three tables and a method note on one scroll, which is the "long undifferentiated scroll" the principles refuse.

Nothing here needs new research or a new engine. It is a week of design and a week of code, and most of it is removal.

## Audit of the Star Shard design practice

Four documents in `starshard.net/` govern design: `UI-PRINCIPLES.md` (the why, 14 Aug), `APP-FRAMEWORK.md` (the map, archetypes and the eleven-component kit, 14 Aug), `WRITING.md` (the house style) and `DESIGN-SYSTEM.md` (tokens, 11 Aug, v1 teal and cream). The `star-shard-design` skill (synced 6 Oct) supersedes the tokens with v2: amber `#FFB000` for "tonight" only, parchment `#F0D89A` everywhere else, Cormorant Garamond 600 for headings, Varela Round for the rest, radius 0, no bevels, glyph icons only. The practice is unusually well argued; the audit question is whether the sim keeps it.

**What the practice commits to, and how the sim scores.**

**Where the practice itself is thin for this product.** UI-PRINCIPLES and APP-FRAMEWORK were written for a phone-first nightly ritual; the sim is desktop-only, members-only, and its "daily" is a run that takes 50 minutes to three hours. Three things the practice does not cover and the sim needs: a rule for *waiting* screens (what a 175-minute run shows at minute 3), a rule for *comparison* (two versions, two weeks, two numbers), and a rule for *uncertainty* (the range, the hatching, the "not counted"). The sim's Design session improvised all three well; they should be written into a short `SIM-PRINCIPLES.md` so the next screen does not reinvent them.

**The one practice gap that matters most.** `DESIGN-SYSTEM.md` measured 118 colours and 32 font sizes on the Star Shard site and called it drift. The sim at 27 and 12 is far better, but it has no written system of its own, and its page already carries three hex values that appear once. The audit's main recommendation is not a restyle; it is to write the sim's tokens down (one page: ground, ink, muted, accent, warn; two type faces and five sizes; one radius) and point Design and Code at the same file.

## Code review: where the sim stands

The codebase is 6,600 lines of plain Node with no dependencies (`package.json` declares none), one Java bridge, and JSON files for state. That is the right weight for a members-only tool on a NAS, and most modules are the size a module should be. Two files are not.

| File | Lines / size | What it owns | Read |
| --- | --- | --- | --- |
| `server.js` | 1,058 / 80 KB | HTTP server, static files, 20 routes (auth, brews, sim, jobs, meta, import, parse, check, codex, plans audit, usage, worker claim and report), the job queue, the extra-games allocator, calibration round robins, daily limits, 17 env vars, 52 functions | The monolith. Every feature of the last week landed here |
| `public/index.html` | 973 / 145 KB | The whole UI: markup for sign-in, join, three-step wizard, sidebar, Coach, Results, Deck, Codex, usage; a 580-line `Component` class; 618 inline styles; 125 literal strings | The other monolith. Design's artboard became the production page by wiring, which was the right call for speed and is now the thing to split |
| `public/support.js` | 1,911 | The Design Component runtime (`DCLogic`, `<sc-for>`, `<sc-if>`, holes) | Vendored from the Design canvas; the page depends on it; fine |
| `score.js` | 194 | Every number the page shows, with a 95% range, by Monte Carlo; play/draw split, Bo3 recombination, empirical-Bayes shrink, calibration uncertainty | The best module in the repo: one place, one method, read by page, coach and allocator alike |
| `calib.js` | 112 | The calibration fit and k | Small and correct; the per-population and recency work from the pilot-questions doc lands here |

The self-play runner lives in `pilot.js` and should move to `tools/` |
| `forge.js`, `worker.js` | 163, 71 | Spawn and parse `forge sim`; the Mac worker's claim/report loop | Fine. `forge.js` reads `SIM_PILOT` to choose bridge vs sim |
| `meta.js`, `realdata.js`, `codex.js`, `coach.js`, `sideboard.js`, `cardstats.js`, `functional.js`, `aihints.js` | 83–254 each | One concern each, as the README's table describes | Good shape; `functional.js` (the Karsten check) is the newest and should read `KARSTEN-SOURCES-VERIFIED.md`'s land-count columns rather than a fixed 25 |
| `tools/` | 9 scripts, 9–85 lines | calcheck, dead-cards, mirror-gate, probe-search, probe-reactive, fidelity-exp, selfplay | The experiments are reproducible from the command line, which is how the pilot work stayed honest |

**What is strong.** The module map in the README matches the files. Every number has a range and one source (`score.js`). Experiments are scripts, not notebooks. The bridge is reviewed, licensed and its changes are marked. State is JSON on disk, which is enough at this scale and trivially backed up. No framework, no build step, no dependency to rot.

**What needs work, in order.**

1. **`server.js`**** by concern, not by line count.** Six files that already exist as sections: `routes/auth.js` (login, logout, me, join), `routes/brews.js`, `routes/sim.js` (sim, jobs, worker claim/report), `routes/codex.js`, `queue.js` (the job queue, the extra-games allocator, calibration round robins), `limits.js` (daily budgets and asks). `server.js` becomes the 100-line file that wires them. No behaviour change, and it is the precondition for anyone but Code touching a route.
2. **The page's logic out of the page.** The 580-line `Component` class moves to `public/app.js`, the markup stays in `index.html`, and the 125 strings that are not data (labels, eyebrows, empty states) stay in markup as the Design format intends. `index.html` drops to the artboard Design can regenerate without losing Code's bindings; the binding list in `NOTE-TO-DESIGN-06OCT.md` becomes a file (`public/bindings.md`) both sessions read.
3. **Tokens as CSS variables.** The page's 27 hex values collapse to about nine roles (ground #0C0C0B, panel #121211, hairline, ink #EDEBE6, muted #8F8D86, dim #5C5B56, accent #C5EC7A, warn amber, and the four matchup colours). Put them in `<helmet><style>` as `--ink`, `--muted`, `--accent` and reference them inline; the 618 inline styles stay inline (that is the Design format's editing model) but stop carrying raw hex. This is the one-page system the audit asks for, in code.
4. **Config in one place.** Thirty env vars across four files, with defaults scattered. A `config.js` that reads them once, names the defaults and prints them at boot (minus secrets) is an hour and removes the class of bug where the NAS and the Mac disagree on `FORGE_XMX` or `SIM_CLOCK`.
5. **Durability of ****`data/`****.** `history.json`, `brews.json`, `calibration.json`, `plans.json`, `codex.json`, `usage.jsonl` are rewritten whole on change (10 `writeFileSync` sites). A crash mid-write loses the file. Write to a temp file and rename, and keep the last three copies. Two hours; the day it matters it saves everything.
6. **Tests for the two modules that carry the numbers.** `score.js` and `calib.js` have no tests; a known-answer test each (a fixed set of games with a hand-computed range; a fixed real/Forge pairing set with a known k) protects the work order's "k is the only metric" rule from a refactor. `node:test` is built in; no dependency needed.
7. **The worker protocol.** `worker.js` claims jobs with a shared token over HTTPS and reports results; the server trusts the report's Forge version string. Add the pilot version and the bridge jar hash to the claim so piloted and unpiloted results never mix, which the pilot-questions doc requires and `pr.pilot` only partly covers.

**Not a problem, and not worth touching.** Plain `http` instead of Express; JSON files instead of SQLite (until a second NAS or a hundred brews); the vendored Design runtime; one JVM per pairing; the Claude calls in `coach.js` and `sideboard.js` being synchronous per run.

**Risk register.** Three things could bite before any of the above: the NAS rebuild that Code's note says is pending (the functional check and the pilot commit are not live until it runs); `env.txt` still sitting in `mtg sim/` with the allow-list (delete it; `.env` on the NAS is the real one); and the `.env` holding an Anthropic key on a box that also serves the public Star Shard site, which the daily budgets limit but do not isolate.

## Canvas review: Brewer v3, screen by screen

Read from the Brewer v3 artboard on the MTG Arena Deck Simulator canvas, the 7 Oct screenshots in the design export, and the live `index.html` it became. The look is settled and good: near-black ground, Manrope at 15/17 with a 34 px display size, JetBrains Mono for anything that is a date, a version or a count, one lime accent, card art as the only colour. It reads as a pro tool, which was the brief. The notes below are about structure, not style.

**Sign-in.** One field pair, one button, one line of context ("Members only. No public sign-up."). The invite flow ("Justin invited you … Join") still exists in markup with no route behind it. Correct as designed; delete the join screen from the page until invites exist.

**Paste your deck (3 steps).** Step 1 is the best screen in the product: a title that is a verb, one paragraph of real help (Moxfield's export path), the textarea, one footnote, one button. It follows the Reading archetype even though it is a form. Step 2 (name and cover, art from the list) and step 3 (check rows, coach note, choose opponents) are right in order. Two cuts: the "Paper deck? Type it in" expander carries three format examples and a scanner-app tip, which is a help page inside a step; link it. And "step 1 of 3" in the top right is the only monospace eyebrow on the page that is not a date or a count; it is fine, but "step 1 of 3" is also the kind of label WRITING cuts when the three steps are visibly three.

**The brew header.** Art, eyebrow (Standard · 1v1 · 1 run), name, version chip, pasted date, two colour dots, and "Run v1" as the single primary action. This is the Page header component done right: eyebrow, title, one action. The two colour dots are decoration unless they are nameable (UI-PRINCIPLES §0: "a mark you cannot name is decoration"); give them a hover label or drop them.

**The run panel (who should it play).** Three options as three equal regions with radio dots, each with a one-line description and a time estimate, then "20 games each · best of three … Queued behind nothing" and "Queue the run". The content is exactly right, including the time estimate at level 1. The form is three cards for one choice; a segmented control or three rows with the description under the selected one would say "one choice" rather than "three things". The footer line is the best status line in the app.

**Coach (Reading).** Monospace eyebrow (now · v1 · Oct 7 field), then "How it's doing" over a 34 px answer ("Running · 1 of 400 games"), one line of state (queued, time left, field), then "The weakness" over a sentence and a paragraph, then one link down ("Results so far →"). This is UI-PRINCIPLES §2c tier 1 transplanted to a desktop tool and it works. One change: "Too early to say" with "You can close this; the run carries on" is the right honesty, but the sentence "Numbers under 30 games show hatched" is method narration on the answer screen; it belongs in Results beside the first hatched number. The composer ("ask the coach") is unwired and shown with a placeholder; hide it until the route exists.

**Results (Reference, currently a scroll).** In page order: status; "Most likely record" and "Top-8 odds likely between … and …"; a share-of-field bar with its own explanatory sentence; "Not played, counted as even"; the matchup table (opponent, verdict, you win, range with 50% marked); "What would raise your top-8 odds most"; "How these numbers were made"; the card table (card, cast, first, won cast, not, difference, dmg/g) with a four-line method note; "What beat you"; the pod. That is nine blocks at near-equal weight and three sentences of method. The archetype says: one page header with the one number and its range as a Stat; then sections of rows (Your matchups; What would raise your odds; How each card played; What beat you), each with an empty state; method and "not counted" as a single disclosure on the row that needs it. The share-of-field bar is a good idea in the wrong place: as the matchup table's first column (a width proportional to meta share) it says the same thing without a second visual language.

**Deck (Collection, currently a stack).** Versions (a timeline: version, date, what changed, result and field), Compare (a diff with an empty state), Field (sources, snapshots), Where you play it, Goal, Considering, Sideboard plans, then the list itself with name-and-cover editing. The archetype says the list is the hero and the largest thing on screen; today it is last. Versions and Compare belong above the list as one row ("v1 · Oct 7 · 48% · compare with →"), and Field, Goal and Considering are three features with one source, no goals set, and a coach that is not connected: three empty states dressed as sections. Show the list, the sideboard plan beside it (that is real and used), and one "Versions" row; bring the rest back when each has content.

**Codex.** Cards, archetypes, terms and characters with Scryfall art, "In plain terms", "How it wins / How it loses / Cards that define it / Your brews against it", members' notes. It is a Reference screen done properly, and it is the one surface where the lore-and-art brief shows. Two lines break the fourth wall ("Summarized from … (CC BY-SA)" is attribution and must stay; "Scraped nightly; every snapshot is kept" is method and should go).

**Across all screens.** Twelve font sizes where five would do (34 display, 22 section, 17 body, 15 secondary, 13 mono and captions); the 12/11/10.5/10 px uses are captions that fail the 11 pt floor in UI-PRINCIPLES §5 at desktop density and should be 13. The 0.6-opacity amber flag line is the one element that uses opacity for meaning; replace it with the muted ink colour and a glyph. The `<img src="{{ … }}">` 404s on load (Code's note) are a Design-format quirk; a `background` style or a guarded `<sc-if>` around each image fixes it.

What the canvas does well is worth saying plainly: it answers first, it names its uncertainty, it uses one accent, it never flatters a result, and the writing is in the house style. The improvements are all subtractions and reorderings; nothing needs a new look.
