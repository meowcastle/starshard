## 2. What failed and why

Nothing failed. Three deviations and choices, stated rather than asked:

**No Docker MySQL in the VM.** `which docker mysqld mariadb` found none, so the packet's "or
SQLite shim" branch was taken. `starshard-api/test/helpers/sqlite-pool.js` is a
`mysql2/promise` look-alike over Node's built-in `node:sqlite` (present in the VM's Node
22.23 and in the Mac's Node 24). It translates `schema.sql` (AUTO_INCREMENT, ENGINE, UNSIGNED,
UNIQUE KEY, INDEX, ON UPDATE CURRENT_TIMESTAMP) and the four MySQL-only constructs the server
uses in queries (NOW(), ON DUPLICATE KEY UPDATE with VALUES(), the `id = id` no-op form, Date
parameters), maps SQLite's unique-constraint failure onto `ER_DUP_ENTRY` with a `sqlMessage`
naming the column so the existing 409 branch works unchanged, and runs with foreign keys on so
cascade deletes are really exercised. `helpers/boot.js` puts the shim into `require.cache`
under the exact path `mysql2/promise` resolves to before `server.js` is required, so
`server.js`'s own `mysql.createPool` lands on it with no test-only branch in the server. What
the shim proves is handler logic, status codes, transactions and cascades. It is not MySQL;
a schema change still wants one run against the real box before shipping.

**Which signup writes birth_data.** CLAUDE.md's privacy invariant says Manzil signup never
writes `birth_data`. The packet says signup "accepts and stores birth fields". Both hold:
the server now tells the two apart by the presence of `five`/`pack`. With them, the body is a
Manzil signup and behaves exactly as before (manzil_pack written, birth_data untouched; the
game's own chart grab still does its separate `PUT /api/me/birth`). Without them, the body is a
Star Shard signup: `birth_data` is written in the same transaction as the user row, and
`manzil_pack` is cast from it on the first `GET /api/me/manzil-pack`. `five`/`pack` present
but malformed is still a 400.

**Which `tz` is the birthplace.** `api.js`'s `signup()` always fills `tz` with the device's
zone when the caller sends none, because the age gate reads it as the region signal. Stored as
a birth zone that would be wrong for anyone born elsewhere. So the server takes the
birthplace zone from a new body field, `birthTz`, and falls back to `tz` only when geocoded
`lat` and `lon` ride along with it (the shape the old star-shard page and Manzil's chart grab
already send). A bare date plus a device `tz` stores no zone. This is a wire-contract detail
for SS8 (the new signup UI should send `birthTz` from the geocoder), and `api.js`'s
header comment ("signup() sends only five integers") is now stale on the Star Shard path.
`api.js` is outside the night shift's write list, so it is queued, not edited.

**The birth instant on the server.** The client's restore uses the restoring device's zone
when a row has no `tz`. The server has no device, so a row with no zone is read as UTC
wall-clock, and a row with no known time is read at noon. The Moon moves about half a degree
an hour against a 12.86 degree station, so this only matters within a sliver of a boundary.
Stated in the module header.
