**What was built, server.** `email_capture` in `starshard-api/schema.sql` with `migrations/2026-11-02-email-capture.sql`: the address (unique), the sha256 of a random id the device made for itself, `user_id` (null until an account with that address exists, cascading when it does), `source` (`shard` or `play`), the device zone, when. `POST /api/email` validates the address and the device id, runs the age gate on the birth date in the body with the request's own region read (same posture as `/api/auth/age-check` and signup; nothing from the date is stored), and inserts; an address that already has an account is linked from the start; a repeated address answers 200 and changes nothing, so the route never says whether an address is known. `DELETE /api/email` with the same device id removes the row while no account owns it. ## 2. What failed and why

Nothing in the gate. Three things to know:

**The game has no field of its own.** The packet sits in the MZ table and the game's first night is still behind its cast. Putting a field in the game means one of the three edits in part 5, each a change to the game copy MZ1 will make (`v1/manzil.html`), not to the live file. The route takes `source: "play"` already.

**`api.js` was not written.** It is the one module that calls `fetch()` and it sits at the repo root, outside the write list. The two calls live in `leave-email.jsx` against its exported `API_BASE` until Justin moves them in (part 5). Nothing else in the shell calls `fetch()` directly.

**The privacy page says nothing about it.** `privacy/` describes what an account needs. An address left without an account is a new thing the service keeps; a sentence for it is pre-drafted in part 5. Legal pages are a decision, so nothing was written there.

Choices made rather than asked:

- **The age gate runs on the server** from the birth date the chart was cast from, with the request's own region read, exactly as signup does; the client also hides the field under thirteen so a child never sees a place to leave an address. The ethics floor asks for an age gate with no incentive to lie, and this one asks nothing new: the date is already on the device for the chart.
- **A repeated address answers 200**, the same body as a first one, so the route cannot be used to ask whether an address is known.
- **The device id is hashed** before it is stored, and only the device that made it can take the row back. Once an account owns the row, the account page's delete is the way.
- **The copy promises only what exists.** Nothing is sent to the address today; SS15 is the nightly mail, and the line says "when the nightly mail begins". No "we", no method, no product sentence.
- **No browser on the Mac's VM**, as before: the smoke ran in the sandbox against the byte-identical build (hashes above). The Mac ran the build, the 230 and the 28.
